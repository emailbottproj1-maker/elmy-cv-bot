# خطة نظيفة — منصة إرسال CV (النسخة الويب النهائية)

## السياق (Context)

العميل محمد (مستقل) يدير **خدمة**: كل عميل من عملائه يرسل له CV، ومحمد يطلق حملة إرسال لذلك الـ CV إلى قائمة شركات. العميل يشتغل من **آيفون/آيباد فقط (بلا لابتوب)** → لازم **منصة ويب**، لا برنامج ديسكتوب.

النظام بُني أولاً كنسخة ديسكتوب (Tkinter) مكتملة ومُختبرة (10/10) — **منطقها الأساسي يُعاد استخدامه بالكامل**، والواجهة فقط تتغيّر إلى ويب + المعمارية تتحوّل لـ serverless.

**القرارات النهائية التي تُنظّف الخطة:**
1. **الاستهداف بـ"باقات" (Packages):** كل حملة لها `package_size` (50/100/200 أو القائمة الكاملة). البوت يختار شركات عشوائية **لم تُستخدم في حملات سابقة**. إذا انتهت الشركات الجديدة (Pool exhausted)، يُكمّل الباقة من الشركات السابقة ويعرض تنبيهاً بعدد المُعاد. القائمة الماستر قابلة للتوسعة بإضافة شركات جديدة في أي وقت.
2. **الذكاء الاصطناعي (Gemini Flash) ميزة أساسية مضمّنة** — يكتب رسالة مخصّصة لكل شركة، مع رجوع آمن (fallback) للقالب لو فشل.
3. **الحد اليومي والتباعد عالميان (Global)** لأن كل الحملات تشترك في إيميل واحد `mddx90@gmail.com` — منعًا لحظر Gmail.
4. **الكود ملك العميل بالكامل** بعد التسليم.

---

## المميزات النهائية المتفق عليها

- منصة ويب تعمل من الآيفون/الآيباد، محمية بكلمة مرور (`Mm123456@@`).
- **حملات متعددة:** حملة لكل عميل — يرفع فيها CV + اسم المرسِل + عنوان الإيميل + نص رسالة التغطية.
- كل حملة تُرسل إلى **قائمة الشركات الكاملة**.
- **AI (Gemini Flash)** يكتب رسالة مخصّصة لكل شركة تلقائيًا.
- تخصيص باسم كل شركة + دعم العربية/الإنجليزية + إرفاق CV.
- **Anti-Spam:** فواصل عشوائية + حد يومي 50 (عالمي) + استئناف تلقائي.
- الإرسال يكمل **24/7 حتى لو الجوال مسكّر** (cron خارجي ينبض السيرفر).
- **Tracking Pixel** + لوحة إحصائيات الفتح لكل حملة.
- قاعدة بيانات شركات ماستر قابلة لإعادة الاستخدام.
- استضافة مجانية (Vercel + Supabase + cron-job.org). الكود ملك العميل. دعم أسبوعين.

## المعمارية (Architecture)

```
الآيفون/الآيباد → متصفح → واجهة ويب (Vercel)
                               │ HTTPS (محمية بكلمة مرور)
                ┌──────────────▼───────────────┐
                │   Vercel Serverless API       │
                │   /login  /campaigns  /upload │
                │   /start  /stop   /stats      │
                │   /tick  ← (نبضة الإرسال)      │
                │   /pixel ← (بكسل التتبع)       │
                └───────┬───────────────┬───────┘
                        │               │
            ┌───────────▼────┐   ┌──────▼──────────┐
            │ Supabase (DB)  │   │ Supabase Storage │
            │ companies      │   │ CV لكل حملة       │
            │ campaigns      │   └──────────────────┘
            │ campaign_sends │
            │ email_opens    │
            │ app_config     │
            └────────────────┘
                  ▲
   cron-job.org (مجاني، كل دقيقة) ──► /tick ──► Gmail SMTP
   (يكمل الإرسال حتى لو الجوال مسكّر)
```

**نموذج cron-tick:** بدل thread على الجهاز (مستحيل على آيفون)، خدمة cron مجانية تنبض `/tick` كل دقيقة. كل نبضة:
1. تتحقق من **الحد اليومي العالمي** (هل أُرسل < 50 اليوم عبر كل الحملات؟) و**التباعد العالمي** (هل مرّ الفاصل منذ آخر إرسال؟).
2. تختار أقدم إرسال `pending` من بين كل الحملات النشطة (round-robin/FIFO).
3. تولّد نص الرسالة (AI أو قالب) → ترسل عبر Gmail → تسجّل `sent` + تحدّد `next_global_send_at` بفاصل عشوائي.

> **مهم:** التباعد والحد عالميان لأن المُرسِل إيميل واحد. تشغيل 3 حملات لا يعني 150/يوم — يبقى 50/يوم إجمالًا موزّعة.

## نموذج البيانات (Supabase)

| الجدول | الحقول الرئيسية | ملاحظات |
|--------|----------------|---------|
| `companies` | company_name, email, language, sector, city | القائمة الماستر، تُبنى مرة |
| `campaigns` | id, customer_label, cv_path, sender_name, subject_ar, subject_en, cover_letter_ar, cover_letter_en, use_ai(bool), status(active/paused/done), created_at | مُدخلات كل عميل |
| `campaign_sends` | campaign_id, company_id, status(pending/sent/failed), tracking_uuid, generated_body, sent_at, error | يُملأ بـ**كل الشركات** عند إنشاء الحملة (استهداف القائمة الكاملة) |
| `email_opens` | tracking_uuid, opened_at, ip, user_agent | موجود ومُختبر |
| `app_config` | key, value | يحوي: gmail, daily_cap, min/max_delay, **last_global_send_at**, sent_today_count/date |

**الاستهداف الكامل:** عند إنشاء حملة، نُدخل صفًا في `campaign_sends` لكل شركة في `companies` بحالة `pending`. التتبّع منفصل تمامًا لكل حملة.

## ما يُعاد استخدامه (جاهز ومُختبر ✅)

| الملف | الدور في الويب |

## وحدات جديدة تُبنى

1. **`bot/ai_writer.py`** — يستدعي Gemini Flash API. مدخلات: اسم الشركة + القطاع + لغة + نص التغطية الأساسي (كنبرة/سياق). مخرجات: نص رسالة مخصّص. **fallback** للقالب عند أي فشل/تجاوز حد. يخزّن الناتج في `campaign_sends.generated_body` (للتدقيق — فريق العميل سيراجع).
2. **`bot/supabase_db.py`** — طبقة وصول Supabase (REST) تستبدل `database.py` محليًا: إنشاء حملة + ملء `campaign_sends` + `next_pending_global()` + عدّادات الحد العالمي + upsert opens.
3. **`api/` (Vercel functions)** — `login`, `campaigns` (list/create), `upload` (CV → Storage)، `start`/`stop`، `tick`، `stats`، بالإضافة لـ `pixel`/`stats` الموجودة.
4. **`web/` (الواجهة)** — صفحات: دخول بكلمة مرور، قائمة الحملات، إنشاء حملة، تفاصيل حملة (تقدّم + إحصائيات). RTL عربي + متجاوب موبايل. (Bootstrap/HTML بسيط أو Next — يُحسم في م.2.)

## الخطة على مراحل (Phases)

### المرحلة 0 — التهيئة (يوم 0)
- استلام كلمة المرور (✅ `Mm123456@@`) + App Password (✅). قائمة الشركات: يبنيها يوسف. عينة CV: أي عينة للاختبار.
- دفعة مقدّمة عبر ضمان مستقل.
- إنشاء مشروعي Supabase + Vercel + ضبط env vars (Gmail, App Password, Gemini key, STATS_TOKEN, SITE_PASSWORD).

### المرحلة 1 — Backend والمعمارية (~1 يوم)
- جداول Supabase أعلاه + Supabase Storage للـ CV.
- `bot/supabase_db.py` + منطق إنشاء حملة يملأ `campaign_sends` بكل الشركات.
- `bot/ai_writer.py` (Gemini) + fallback للقالب.
- `/api/tick`: الحد/التباعد **العالمي** → اختيار pending عبر الحملات النشطة → توليد body (AI/قالب) → إرسال → تسجيل + `last_global_send_at`.
- **اختبار:** حملتان بـCV مختلف → نبضات `/tick` ترسل بالتناوب، تحترم 50/يوم العالمي، وكل حملة تستهدف القائمة كاملة.

### المرحلة 2 — واجهة الويب (موبايل أولًا) (~1.5 يوم)
- دخول بكلمة مرور.
- قائمة الحملات + حالة كل وحدة + "حملة جديدة".
- نموذج إنشاء حملة: رفع CV + اسم + عنوان + نص تغطية AR/EN + مفتاح تفعيل AI.
- تفاصيل الحملة: ابدأ/إيقاف، شريط تقدّم + عدّاد ("45 من N — اليوم 12/50")، لوحة إحصائيات الفتح.
- RTL + متجاوب مع الآيفون.
- **اختبار:** إنشاء وتشغيل حملتين من متصفح جوال فعلي.

### المرحلة 3 — الربط والنشر (~1 يوم)
- نشر Vercel + env vars + تفعيل البكسل على الإنتاج.
- إعداد cron-job.org (كل دقيقة → `/tick`).
- اختبار إرسال حقيقي (5 إيميلات) + mail-tester (≥8/10) + AI يولّد نصًا سليمًا.
- اختبار "الجوال مسكّر والإرسال يكمل".

### المرحلة 4 — اختبار نهائي + تسليم (~0.5 يوم)
- E2E كامل + إصلاح أخطاء.
- دليل عربي مختصر + screenshots.
- تسليم: رابط + GitHub repo (الكود ملك العميل) + مكالمة شرح.

## نقاط مخاطر + تخفيف

| المخاطرة | التخفيف |
|---------|---------|
| Vercel cron مجاني = مرة/يوم فقط | cron-job.org خارجي مجاني (كل دقيقة) |
| تعدد الحملات يتجاوز حد Gmail | **حد وتباعد عالميان** (50/يوم إجمالًا عبر كل الحملات) |
| نفس الشركة تستقبل عدة CV (سير العمل الكامل) | مقصود ومؤكّد من العميل؛ موثّق صراحةً |
| Gemini يفشل/يتجاوز الحد المجاني | fallback تلقائي للقالب؛ 50/يوم ضمن الحد المجاني |
| Tracking pixel يُحجب أحيانًا | نتائج تقريبية موضّحة للعميل |
| App Password/كلمة المرور حساسة | في Vercel env vars فقط، لا تُكشف بالواجهة |
| فريق العميل سيدقّق | `generated_body` محفوظ للتدقيق + كود نظيف موثّق |

## خطة التحقق (Verification)

1. **وحدات معاد استخدامها:** `python tests/run_all.py` يبقى أخضر (10/10).
2. **`/tick` يدوي:** ينشئ حملتين → نبضة ترسل من الحملة الصحيحة ببياناتها، تحترم الحد العالمي، وتحدّث `next/last_global_send_at`.
3. **AI:** التحقق أن `generated_body` نص معقول مخصّص باسم الشركة، و fallback يعمل عند تعطيل المفتاح.
4. **من متصفح جوال:** دخول → إنشاء حملة → رفع CV → ابدأ → مراقبة العدّاد.
5. التأكد: وصول Inbox (mail-tester ≥8/10)، اللغة الصحيحة، CV مرفق، الفواصل عشوائية، التوقف عند 50، الإرسال يكمل والجوال مسكّر، الفتح يظهر بالإحصائيات.
6. اختبار العميل: 5 إيميلات حقيقية أمامه → تحرير الدفعة.
